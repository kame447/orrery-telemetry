# Process-bound status proof for fresh MCP (fork prototype)

Saved settings alone do not prove that the process currently answering a writable MCP endpoint runs with the intended authority. This standalone verification module is a component for a later opt-in service-management PR. It does not install, update, restart, stop, or reconfigure any service.

The function `probe()` in `integrations/chatgpt_mcp/src/orrery_chatgpt_mcp/fresh_process_probe.py` accepts an operator-confirmed LaunchAgent label, plist path, port, privately held pairing secret, and fixed Mail instance/sender/recipient IDs. These inputs must never be taken from a model-facing MCP request or an untrusted conversation.

It first checks the loaded plist and PID through `launchctl print`, then verifies using `lsof` that the server side of the exact new 127.0.0.1 TCP connection belongs to that PID. It checks the PID again. Failure occurs before sending the pairing secret. On that same verified connection it validates the MCP initialize protocol version and tools capability, sends notifications/initialized and checks its 202 response, then calls tools/list and orrery_status. The socket remains pinned throughout, including the notification, to prevent secrets being sent to an unverified reconnect. After the final status RPC, the probe also rechecks that launchd still reports the same PID; a changed, vanished, or unverifiable service is a refusal. This verifies only a point-in-time observation, not continuous future uptime.

The effective response must expose exactly three read tools and three fresh-message tools. It must match the explicitly expected fresh Mail instance, stable sender ID and allowed recipient ID/name/kind set, and report message_enabled_on_server=true, spawn_enabled_on_server=false, read_only=false, approval_mode=operator_delegated and unknown_recovery=authenticated_receipt_read. Extra tools or recipients cause a refusal. The result omits the secret, message body, credentials and arbitrary response fields.

This is a live connection/process identity proof, not a code-integrity proof. A later service installer must verify the pinned release and actual launchd ProgramArguments before using it. Do not infer the active grant from stored plist settings, bypass the listener-owner proof or treat a synthetic check as an attended production acceptance.

No existing legacy MCP gateway, Tunnel, Mail or running agent was changed. Real macOS launchd/lsof integration had not been tested when this initial component was written; subsequent isolated Mac acceptance is documented separately. Synthetic cases use a temporary loopback HTTP server and mocked launchctl/lsof responses to check the intended grant, swapped PID, foreign listener, changed recipient scope and unexpected tools. Four cases were added for incorrect initialization versions, rejected initialization notifications, and launchctl/lsof timeouts that must fail before the secret is transmitted. The initial 21-case run had been unverified. Stage 29 added two post-RPC PID cases; the resulting 23 component cases are covered by a Mac isolated Python run of 51 related tests plus 30 subtests, and an expanded run of 134 tests with documentation/link checks. Further actual LaunchAgent acceptance is tracked separately.

Run `python -m unittest discover -s integrations/chatgpt_mcp/tests -p test_fresh_process_probe.py` for the synthetic tests. This PR supplies a verification component, not a completed service status/start/stop CLI.
